{{ 'Versioning mappings' | translate }}
Top

{{ 'Overview' | translate }}

Every mapping keeps a history of versions. Editing a mapping no longer changes the running configuration directly — instead your changes are saved to a draft. You then publish the draft to create a new immutable version, and activate the version you want to run. This lets you change a mapping safely, review what changed over time, and roll back to a known-good configuration at any point.
Key rule: at most one version of a mapping is active at any time. Activating a version automatically deactivates the previously active one, so there is never any ambiguity about which configuration is processing messages.

{{ 'The version lifecycle' | translate }}

The full flow when working with a mapping is:
  1. Edit → Save — your changes are stored in the mapping's single draft. The active configuration keeps running unchanged. A draft badge appears in the mapping list.
  2. Publish the draft — the draft becomes a new, immutable version (v1, v2, v3…). You can attach an optional label (a change note) when publishing. Publishing does not activate the version.
  3. Activate a version — its configuration is loaded into the running mapping. To roll back, simply activate an older version; newer versions are kept and remain available.
Note
The first time you publish or activate a mapping that has no versions yet, its current active configuration is automatically captured as v1, so no history is lost.

{{ 'The Versions view' | translate }}

Open the version history from the mapping list: click the ⋮ (actions) menu of a mapping and select Versions. A drawer lists every record of that mapping in a single grid — the current draft and all published versions — each tagged with its State:
  • active — the version currently running.
  • published — an immutable version you can activate or delete.
  • draft — unpublished edits waiting to be published.
Each row offers contextual actions in its ⋮ menu: Publish (on the draft), Activate and Delete (on inactive published versions), and Edit label (on any published version). The active version cannot be deleted — activate another version first.

Description: The Versions drawer for a mapping.

{{ 'Version and draft indicators in the mapping list' | translate }}

The Status column of the inbound/outbound mapping list shows, at a glance, the active version of each mapping (for example v2) and a draft badge when the mapping has unpublished changes that have not yet been published.

Description: The mapping list Status column showing the active version badge and a draft badge.

{{ 'Labels (change notes)' | translate }}

A label is a free-text note describing what a version contains or why it was created. You can set a label when publishing a draft, and you can change it later for any published version via Edit label in the Versions drawer. The label is the only field of a published version that can be edited — everything else is immutable.

{{ 'Configuring how many versions are kept' | translate }}

To bound storage, only the most recent versions of each mapping are retained. The limit is configured per tenant under Configuration → Service configuration → Caching in the field Number of mapping versions to retain (default 10). When a new version is published, versions older than this limit are deleted — the active version is never deleted, even if it falls outside the retention window.

Description: The "Number of mapping versions to retain" setting under Service configuration → Caching.

{{ 'Relationship in the inventory' | translate }}

Each version is stored as its own managed object (type d11r_mapping_version) and is registered as a child addition of the mapping's managed object. This makes the mapping → versions relationship navigable directly in the Cumulocity inventory and from external tooling, independently of the mapper UI.
